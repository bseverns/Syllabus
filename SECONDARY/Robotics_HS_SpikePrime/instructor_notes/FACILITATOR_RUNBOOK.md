# SPIKE Prime Robotics — Facilitator Runbook

Use this runbook with the 12 short session plans. It supplies the repeated timing, novice supports, evidence checks, and recovery moves that those plans assume.

## Required preflight

Complete this on the same device type students will use:

- open the SPIKE App and create, name, save, close, and reopen a project;
- connect to each uniquely labeled hub and run both drive motors;
- check hub charge, motor ports, sensor ports, and firmware/app compatibility;
- open the correct official Driving Base instructions;
- mark a start box and safe test lane;
- build the maze and SuGo ring and remove trip hazards;
- print or post the student handouts and reflection prompts;
- prepare one paper route/code-trace set for every team in case a device is unavailable.

Do not launch real robot runs until the facilitator has verified the room, equipment, and local safety expectations.

## Per-team materials

- one complete SPIKE Prime kit with labeled hub;
- one charged app-compatible device and charger access;
- Driving Base parts and the sensors named in the session;
- masking tape, paper, pencil, measuring tape, and team folder;
- printed or open copies of Build Instructions, Coding Tutorials, Challenge Cards, and Reflection Prompts.

Room materials: display, timer, spare sorted parts, charging area, `tested / needs checking` bins, maze, SuGo ring, and a clearly marked robot parking area.

## Default 60-minute rhythm

| Time | Move |
| --- | --- |
| 0–7 min | Welcome, safety check, and one visible session target |
| 7–15 min | Demonstrate one new build or code move |
| 15–35 min | Team build/code round; driver and navigator switch halfway |
| 35–40 min | Stop programs, park robots, and reset the lane |
| 40–52 min | One controlled test per team, followed by one revision |
| 52–60 min | Save with a new version name, reflect, inventory, and park |

If builds take longer, preserve the final eight minutes and continue next session. Do not sacrifice shutdown, parts inventory, or saved evidence.

## Session launch map

| Session | Prep and demonstration | Evidence before cleanup | If the technology fails |
| --- | --- | --- | --- |
| 1 | Stage sorted kits; show safe part/cable handling and hub labels | Build inspection and team-role check | Continue the build; use a paper parts/ports map |
| 2 | Demonstrate save/version naming and one motor block | Straight run plus predicted/actual distance | Arrange paper motion blocks and calculate a route |
| 3 | Show a loop and one turn-calibration test | Square or figure-eight plus one adjusted value | Trace the loop on a floor/paper grid |
| 4 | Display live sensor values before coding a response | Three readings and stop-on-color behavior | Sort sample readings and write the trigger rule |
| 5 | Mark obstacles and a one-robot test lane | Avoidance test and one conditional revision | Role-play sensor/robot commands with event cards |
| 6 | Walk the maze and model a route sketch | Strategy sketch and first-run failure point | Simulate the route on the printed maze |
| 7 | Model changing only one threshold or turn value | Full run or documented best partial run plus revision | Compare trace results and choose one parameter change |
| 8 | Review ring boundaries and safe retrieval; inspect attachments | Configuration sketch and inspection | Analyze sample configurations; build without powered runs |
| 9 | Model edge detection before opponent detection | Safe autonomous practice and observation note | Trace state/decision cards for a mock round |
| 10 | Prepare a simple match-observation sheet | One evidence-based code or build change | Review supplied or prior observations |
| 11 | Stage inspection and backup stations | Saved final version, port map, and inspection | Complete paper inspection and strategy rehearsal |
| 12 | Post roles, bracket/rotation, stop signal, and reflection station | Role participation, final reflection, and parts return | Run strategy tabletop rounds and team retrospectives |

## Language for students new to technology

Say this in Session 1:

> You are not expected to arrive knowing robotics or coding. We will build one behavior at a time. Your job is to predict, test safely, notice what happened, and choose one next change.

Define and point to each term:

- **hub:** the robot's small computer and power source;
- **port:** a labeled place where a motor or sensor cable connects;
- **block:** one instruction in the SPIKE program;
- **program:** the ordered instructions the hub follows;
- **sensor:** a part that measures something around the robot;
- **threshold:** the value where the program changes what it does;
- **loop:** instructions that repeat;
- **conditional:** an instruction that runs only when a condition is met.

Do not use typing speed, previous LEGO experience, winning, or willingness to drive the robot as evidence of mastery.

## Team roles and access

Use at least three rotating roles: `builder/driver`, `navigator/reader`, and `recorder/safety checker`. A student may participate through planning, parts finding, reading, coding, measurement, observation, documentation, repair, or match operations.

- Read and demonstrate instructions; do not rely on text alone.
- Offer enlarged screenshots, paper block cards, and a printed maze.
- Keep test paths reachable and provide a table-height route when floor access is a barrier.
- Allow observation or strategy roles without requiring close contact with moving robots.
- Use color plus labels/shapes; never make color the only signal.

## Common-stuck guide

Use the same check order: **power → connection → port → program start → one small test**.

| What you see | Next move |
| --- | --- |
| Hub will not connect | Confirm charge and hub label; close other connections; use the paper trace while retrying |
| Robot moves backward or spins | Compare motor port/orientation with the demo; test one motor at a time |
| Sensor seems ignored | Display the live reading, check its port, then test the conditional with an obvious input |
| Turns drift | Mark the start pose; reduce speed; repeat the same turn three times before changing one value |
| Team changes many blocks | Restore the last saved version and change one block/value |
| One student controls everything | Stop, name roles, and switch driver/navigator before the next run |
| Robot breaks during a run | Stop the program, retrieve only after the signal, photograph/mark the failure, and repair in parking |
| No working device remains | Continue with route sketches, paper blocks, prediction tables, observation, and design revision |

## Evidence and completion

Each team folder should contain a build/port check, at least three named program versions, sensor or movement observations, a maze revision, a SuGo strategy/configuration sketch, and final reflection. Winning a match is not required. Instructor inspection—not a file upload or self-report—controls robot and ring readiness.
