# Debugging Studio — Facilitator Launch Guide

Use this guide with the eight session plans. It supplies the repeatable room routine, material plan, novice supports, and recovery moves that the short session files assume.

## Launch decision

This course can run with code, robots, media projects, or an unplugged process. Choose **one shared system** before announcing the course. Do not ask students to learn an unfamiliar production tool and the debugging process at the same time unless tool instruction is part of the schedule.

Before Session 1, confirm:

- every student can open or handle the chosen system;
- saving, naming, and reopening work succeeds on a student device;
- you have one working example and one deliberately broken copy;
- private work storage is available;
- the handouts can be printed or opened without extra sign-in;
- students have a no-account, no-device route using printed process cards.

## Minimum materials

For every two students:

- one accessible example system or printed process puzzle;
- one copy of the current handout;
- paper or sticky notes and a pen or marker.

For the room:

- display or large paper for a live model;
- timer;
- three prepared broken examples at easy, medium, and stretch levels;
- a visible `What we know / What we tried / What happened / Next test` board;
- optional devices, robots, or media tools for the selected platform.

The minimum viable version uses no student accounts: print the handouts and debug paper instructions, object-sorting rules, a drawn route, or a sequence of event cards.

## Default 75-minute rhythm

Use the same rhythm each session so students can focus on the problem rather than guessing what class expects.

| Time | Move |
| --- | --- |
| 0–8 min | Welcome, show the session question, and define unfamiliar words. |
| 8–18 min | Model one short bug aloud without rushing to the fix. |
| 18–25 min | Introduce the handout and show a completed example. |
| 25–47 min | Paired debugging round; pause once for an evidence check. |
| 47–52 min | Screen/body break and materials reset. |
| 52–65 min | Revise, swap roles, or run one new test. |
| 65–75 min | Save evidence, complete reflection, and preview the next session. |

For 60 minutes, shorten both work rounds. For 90 minutes, add a second case; do not lengthen the opening talk.

## Session prep and completion evidence

| Session | Prepare before students arrive | Minimum evidence to keep |
| --- | --- | --- |
| 1 | One code bug, one confusing interface, and one unplugged sequence error | One debugging-log entry naming evidence and a next test |
| 2 | A task with missing or competing directions | A stuckness map plus one useful next move |
| 3 | A scenario where speed, prevention, and learning point to different choices | A goals reflection that explains one priority |
| 4 | A short, low-stakes bug and private emotion check-in route | A private check-in plus one chosen support move |
| 5 | Two working solutions with different readability or efficiency | A before/after comparison naming a tradeoff |
| 6 | A vague bug report to improve and paired role cards | A reproducible bug report and peer-coaching note |
| 7 | Shared cases for students without a suitable personal project | Case-study draft with tests and results |
| 8 | Portfolio checklist and a private presentation alternative | Required portfolio pieces and final reflection |

## Language for students with limited tech exposure

Say this plainly at the start:

> You do not need to be “a computer person” to do this course. Debugging means noticing what happened, describing it, trying one small change, and checking again. You may speak, point, draw, or write to show your thinking.

Define terms the first time they appear:

- **system:** connected parts that do something together;
- **bug:** a result that is wrong, surprising, confusing, or harmful for the current goal;
- **evidence:** something observed, not just a guess;
- **test:** one safe action used to learn more;
- **revision:** a change made because of what a test showed;
- **refactor:** reorganizing a working process without changing its intended result.

Never use speed, typing fluency, prior coding vocabulary, or willingness to present publicly as a proxy for debugging skill.

## Access and participation routes

- Read prompts aloud and keep them visible.
- Let students draw, dictate, point, or photograph a sequence instead of writing full paragraphs.
- Pair by role: `driver` handles the system and `navigator` tracks evidence; switch at a named time.
- Offer printed screenshots or event cards when screen reading, login, bandwidth, or motor access becomes a barrier.
- Keep emotion check-ins private by default. Students may name a needed support without naming a feeling.
- Provide a private or recorded share-out option in Session 8.

## Common-stuck guide

| What you see | Ask or do next |
| --- | --- |
| Random changes | “What is one thing we can hold still while we test one change?” |
| “It doesn't work” | “What did you expect, and what did you observe instead?” |
| A partner takes over | Return to driver/navigator roles; the navigator may ask but not touch. |
| A student has no technical project | Use the prepared shared case or unplugged sequence. |
| The example itself fails unexpectedly | Model the process: name the new evidence, preserve the file/object, and move to the backup copy. |
| The bug is fixed immediately | Ask the student to reconstruct why the fix worked and design a test that would catch it again. |
| Frustration is rising | Offer a two-minute pause, a smaller case, a role change, or a paper trace without penalty. |

## Safety, privacy, and boundaries

- Do not use real passwords, private messages, student records, or identifying screenshots as cases.
- Use copies of files; never invite experimentation on live school systems or production equipment.
- Follow the selected platform's physical safety rules. Instructor approval controls robot, machine, or powered-tool operation.
- Treat emotional reflections as private learning records, not public critique material.
- Redact names, account details, filenames, and notifications before any optional gallery sharing.

## End-of-course launch check

A student has completed the course when the portfolio shows a described problem, observed evidence, at least one controlled test, a result, a reasoned next move, and reflection on support or tradeoffs. The bug does not have to be fixed.

After each delivery, record the platform used, timing changes, failed examples, access supports used, and material quantities before the next launch.
