# Syllabus — Local AI, Archives & Small Tools

## Course snapshot

- **Promise:** learners make a bounded archive helper or simulated workflow whose sources, uncertainty, and permissions remain visible.
- **Group / staffing:** 8–16 learners; one lead with technical support recommended for any local-model toolchain.
- **Final share:** corpus audit, workflow/prototype, provenance display, and limits statement.
- **Agreement:** *The source is part of the answer.*

## Materials and preflight

A small permissioned document set; source/corpus audit template; computer pairs; one host-approved tool path or a paper retrieval simulation; sample records with varied metadata; provenance cards; and an offline fallback packet.

**Preflight:** confirm learners have permission to use every document in the selected corpus. Do not upload confidential records, student work, personal data, copyrighted material outside its permitted use, or identifiable audio/images to a hosted AI service. Decide storage/deletion rules. Test the exact local/hosted tool and retain a no-account, paper-based path.

## 110-minute session rhythm

15-minute encounter; 20-minute tool/workflow demonstration; 45-minute studio work; 10-minute reset; 15-minute critique; 5-minute evidence parking.

## Four-session sequence

### Session 1 — Define a narrow task and a lawful corpus

**Target:** distinguish a useful bounded question from a general-purpose AI fantasy.

**Prompt:** *What should this helper do, for whom, and what must it never receive?*

**Build/play:** learners select a permissioned corpus, audit its gaps/metadata, and write a task boundary.

**Evidence:** corpus/permission audit and `does / does not` tool statement.

### Session 2 — Retrieval, annotation, and provenance

**Target:** practice finding/supporting claims without hiding the source trail.

**Prompt:** *Could another person see why this answer was offered?*

**Build/play:** teams test a search, retrieval, annotation, or paper-based equivalent across a small document set.

**Evidence:** annotated result with source links/identifiers and one uncertainty.

### Session 3 — Build the smallest helpful interface

**Target:** make a constrained input/output workflow rather than a generic chatbot.

**Prompt:** *What should a user be able to check or correct?*

**Build/play:** teams create a prototype, form, script, or documented workflow that exposes sources and recovery steps.

**Evidence:** user flow plus failure/abstention condition.

### Session 4 — Test trust and handoff

**Target:** test whether a user understands scope, provenance, and limits.

**Prompt:** *What would make someone trust this too much?*

**Build/play:** learners run a peer test, revise the provenance/limits display, and complete a concise operator guide.

**Evidence:** test note, final prototype/workflow, and `how to trust / not trust this` guide.

## Access, safety, and recovery

The core course works with printed documents, cards, and a human “retrieval” role; software is an extension, not a gate. Learners may audit, annotate, design, test, or document. If a model/tool fails or cannot be approved, retain the paper workflow and focus on provenance, interface, and decision boundaries.

## Assessment and partner description

Observe: scopes a task; audits consent/provenance; keeps source evidence visible; identifies uncertainty/failure; creates a workflow another person can inspect and challenge.

**Partner description:** A small-tools studio where learners work with archives and AI systems without hiding sources, consent, or uncertainty behind a fluent answer.
