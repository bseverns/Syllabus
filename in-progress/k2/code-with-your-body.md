# Code With Your Body

> **PILOT syllabus.** Follow the shared [K–2 operating model](README.md). The closest local lineage is [Scratch Game Design](../../PRIMARY/Scratch-Game-Design-Animation_Grades3-5/README.md); this keeps sequence, event, and debugging ideas physical and screen-free.

## Course snapshot

- **Promise:** learners give clear instructions, test them with bodies and objects, notice a bug, and change one command to make a path work.
- **Group / staffing:** 8–12 learners; one lead, with an assistant recommended for large movement groups or individualized mobility/communication support.
- **Final share:** pairs create a three-to-five-card movement routine another pair can run.
- **Community agreement:** *We debug the instruction, not the person.*

## Materials for 12 learners

**Core tote:** 48 large picture-command cards (forward, stop, turn, clap, jump/alternate action, repeat, start, finish); 12 role cards (coder, runner, debugger); painter's tape; 12–16 soft cones or floor markers; 12 clipboards; crayons; 12 dry-erase sleeves or reusable sequencing strips; and one large start/finish sign.

**Helpful extras:** beanbags, floor arrows, a small table-top grid, wheelchair-accessible route markers, and a facilitator camera for documentation only.

**Prep:** tape a short, wide path with an accessible alternate route; make command cards high contrast; pre-select an action menu that works for the learners in the room; post `try / notice / change / try again`.

## Four-session sequence

### Session 1 — Commands make a path

**Target:** use one visible command to change an action.
**Prompt:** *What happens when the card says go, stop, or turn?*
**Demo:** adult follows cards literally, including a silly wrong turn; learners identify the command that caused it.
**Build/play:** practice command-response games in a circle, then use two-card paths.
**Evidence / parking:** learners place cards in an order and show/describe what the order does.

### Session 2 — Give a partner a route

**Target:** sequence three commands for a partner or object.
**Prompt:** *How can we get from start to finish?*
**Demo:** make a three-card route on the floor; narrate one command at a time.
**Build/play:** pairs choose coder, runner, and observer roles; use a body, beanbag, or tabletop token according to access needs.
**Evidence / parking:** mark one route that worked and one card that needed changing.

### Session 3 — Hunt a bug

**Target:** identify a mismatch between the intended path and the instruction cards.
**Prompt:** *What went wrong, and which card should we change?*
**Demo:** facilitator deliberately adds a wrong turn; model neutral language: `The route did not match the cards.`
**Build/play:** pairs receive or invent a short bugged route, test it, swap one card, and test again.
**Evidence / parking:** facilitator records a learner's `before / after` explanation or points to the changed card.

### Session 4 — Invent a routine

**Target:** make a routine another team can follow.
**Prompt:** *What should another team do first, next, and last?*
**Demo:** combine start, movement, repeat, and finish into a four-card routine.
**Build/play:** pairs create a three-to-five-card route or dance; another pair runs it and offers one clear observation.
**Evidence / share:** learners share the routine and name one revision made after testing.

## Safety, access, and failure backup

Participation is never tied to running, jumping, standing, or speaking. A learner can code with cards, direct a partner, move a token, use an AAC device, or observe/identify the bug. Keep routes wide, avoid collisions, and use soft markers only.

If a floor route is too activating, move to table-top tokens and the same command cards. The learning goal is sequence and revision, not gross-motor intensity.

## Assessment and public description

Use the shared four look-fors, plus: **the learner changes an instruction after seeing a result.**

**Partner description:** A fully unplugged introduction to coding logic where young learners use cards, movement, and debugging games to make instructions clearer.

## Pilot review after delivery

Record: which command icons were understood without explanation, whether the route width worked for all learners, which role rotations held attention, and whether four-card routines were the right ceiling.
