# Week 4: Prototype Sprint I

## Teacher at a glance
- **This week is for:** building the first working version fast.
- **By the end of the week:** every team should have a rough prototype that does something real.
- **Prep first:** project bins, pulled materials, labels, and visible repair/testing tools.
- **Project:** the prototype loop in the [course visual pack](../../assets/course-visuals/README.md).
- **Watch for:** teams trying to build the full final version instead of one testable version.

## Big idea
Rough first versions teach faster than perfect plans.

## Weekly goals
- build the first working version of the capstone
- make the main interaction or system real as early as possible
- label parts, save evidence, and protect continuity across long sessions
- use testing and revision language from the start

## Long-session rhythm
Each 1.75-hour session should include:
- 10 min launch / prompt
- 10 min demo
- 30 min build sprint 1
- 10 min break / movement / reset
- 30 min build sprint 2
- 15 min share / document / park / cleanup

Use the reset block to stop part sprawl, relabel loose pieces, and relaunch one clear build target for sprint 2.

## Must-have materials this week
- team-specific project materials
- labels, tape flags, and markers
- repair tools and spare batteries
- project planners and status cards
- clear storage bins and shelves

## Nice-to-have materials
- color-coded tape for systems
- extra connectors, adapters, and cardboard reinforcements
- photo device for version tracking
- small “testing / repairing / ready to park” signs

## Fastest successful build or minimum viable output
One rough prototype with one core function working.

## Session 1
### Objective
Get every team moving on the main project function immediately.

### Launch / prompt
What has to work first for this project to count as real?

### Demo focus
Model rough prototyping: visible wiring, quick structure, labeled parts, and fast testing.

### Build sprint 1
Teams begin the core interaction, mechanism, or structure.

### Break / reset
Quick stand-up: what is working, what is still missing?

### Build sprint 2
Teams keep building toward one working proof rather than many unfinished features.

### Share / document / park
Save one photo and one sentence: “Today we got to…”

## Session 2
### Objective
Strengthen the first working behavior and make the build easier to understand.

### Launch / prompt
What part of your project is still only an idea?

### Demo focus
How to protect what already works while adding one clear next layer.

### Build sprint 1
Teams improve the main function or structure.

### Break / reset
Partner test with one simple question: “What do you think this does?”

### Build sprint 2
Teams add one more layer of audience clarity, structure, or system connection.

### Share / document / park
Update the status card with one success and one risk.

## Session 3
### Objective
Connect systems without losing readability.

### Launch / prompt
What should the visitor notice first?

### Demo focus
Show a small systems map and explain star feature vs. support feature.

### Build sprint 1
Teams connect a second system or strengthen the main system’s response.

### Break / reset
Mid-sprint part check and fast-fix moment.

### Build sprint 2
Teams revise layout so the project still makes sense to an outside viewer.

### Share / document / park
Capture one systems sketch or labeled photo.

## Session 4
### Objective
End the sprint with a usable first version and a clear plan for Week 5.

### Launch / prompt
What did the first prototype teach that the plan could not?

### Demo focus
Model a short prototype review: what works, what fails, what needs reinforcement next.

### Build sprint 1
Teams run a structured test and collect evidence.

### Break / reset
Short conference with staff or peers.

### Build sprint 2
Teams make one targeted change and prepare a Week 5 repair/clarity plan.

### Share / document / park
Every project ends the week with a current-version photo and a named next step.

## Grades 3–4 adaptation
Keep the target tight and concrete:

- build one working action first
- label one important part or pathway
- leave one next-step note that makes re-entry easy next session

## Grades 5–7 extension
Use a more precise extension path:

- compare two prototype versions and choose the stronger one
- add a second system only after the first works
- document which change actually improved the build

## If tech fails, do this instead
Prototype structure, signage, interaction flow, and audience use in cardboard and labels. The core question is still whether the idea becomes real enough to test.

## Documentation target for the week
At least one current-version photo or sketch per session, plus one status-card update naming progress and risk.

## What success looks like
- rough prototypes exist by midweek
- teams know what is working and what is still weak
- project continuity is strong across sessions

## What success sounds like
- “This version is just to test…”
- “We got the main part working.”
- “Next we need to fix…”

## Facilitator notes
- insist on labels, parking, and version capture
- stop teams from disappearing into decorative detail before the main function works
- praise rough progress that answers a real question
- if sprint 2 starts collapsing, shrink the target and protect a useful parking state

## Capstone continuity notes
Prototype week is not a side phase. This is the capstone becoming real. Keep all project talk tied to audience and use.
