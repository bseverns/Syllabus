# Scratch Arcade Adventure — Beginner Bridge and Launch Check

This is an intermediate game-design course. Use this guide to make placement fair, support students with limited device experience, and run a short bridge when students have the ideas but not yet the named Scratch habits.

## Do not use prior exposure as a gate by itself

Before Week 1, invite students to complete four visible tasks on a small practice project:

1. open a project and make a sprite move;
2. connect `when green flag clicked` to two or more blocks;
3. use a loop or `if` block with coaching;
4. name, save, close, and reopen the project.

A student is ready if they can complete these with a picture card, peer prompt, read-aloud direction, or one reminder. Fast mouse use, typing speed, English fluency, owning a device, and knowing vocabulary from memory are not prerequisites.

If a student cannot yet complete the tasks, use the two-session bridge below or place them in `Scratch Stories and Games` first. Do not drop a first-time user into the advanced Week 1 build and call the resulting struggle a motivation problem.

## Plain-language welcome

Say this before the launch check:

> You are not being tested on how fast you use a computer. You may ask us to point, read a block aloud, or show one step again. We are checking which starting point will let you build a game and learn new systems without spending every class fighting the controls.

Words to demonstrate rather than merely define:

- **sprite:** a character or object;
- **stage/backdrop:** the space or scene behind the sprites;
- **script:** connected instruction blocks;
- **event:** the signal that starts a script;
- **loop:** blocks that repeat;
- **conditional:** blocks that choose based on a rule;
- **variable:** a named value that can change, such as score;
- **broadcast:** a named message that lets parts of the project coordinate.

## Two-session bridge

Run this before the 12-week sequence. Use the same device, browser/app, login route, and storage method planned for the course.

### Bridge A — Open, move, save

**Target:** create a tiny project that opens, moves, and can be found again.

**60-minute plan:**

- 0–8: identify mouse/trackpad, keyboard, green flag, stop, sprite, and stage;
- 8–15: model dragging one block and snapping it beneath an event;
- 15–30: make a sprite move, turn, and say something;
- 30–35: body/screen break;
- 35–48: add a short repeat and change one number;
- 48–60: name, save, close, reopen, and record where the project lives.

**Evidence:** the student can start the script and reopen the named project with available supports.

### Bridge B — Rule, score, restart

**Target:** build a one-screen collect-or-avoid loop.

**60-minute plan:**

- 0–8: reopen the project and review the shared words;
- 8–15: model one `if touching` rule;
- 15–30: add a goal object and change a score variable;
- 30–35: body/screen break;
- 35–48: add a hazard or edge rule and a green-flag reset;
- 48–55: partner test using `I expected / I observed`;
- 55–60: save a new version and name the next step.

**Evidence:** the project has an event, a repeated check, a changing variable, and a reset.

## Materials and setup

- one Scratch-capable device per student or pair;
- the actual account/class-studio route, tested on a student device;
- mice when trackpads are a barrier;
- headphones as an option, never a requirement for core directions;
- printed block-shape/vocabulary cards and a screenshot of the save/reopen route;
- the teacher-made starter from `../05_Starter-Project_Build-Recipe/` rebuilt in the local Scratch version;
- paper pitch card and pencils for device downtime.

Before launch, confirm Scratch loads, projects save/reopen, sharing settings match host policy, sound works only where needed, and browser/device restrictions do not block the starter.

## Supports throughout the course

- Keep demonstrations under seven minutes and leave the finished block stack visible.
- Say a block's color, category, shape, and purpose; never rely on color alone.
- Pair with rotating `driver` and `navigator` roles. The navigator points and asks; they do not seize controls.
- Give students the starter architecture when blank-project setup would hide the week's actual learning target.
- Accept a smaller complete game: two stages can replace three when access time, device interruption, or the bridge shortens the build calendar. Keep title, instructions, one changing system, win/lose state, testing, and reflection.
- Let students explain with speech, pointing, screenshots, or a short recorded walkthrough instead of typing long reflections.

## Recovery paths

| Problem | Keep learning moving |
| --- | --- |
| Student cannot sign in | Use an offline/local editor if approved or pair on a class project; record who owns the saved file |
| Project was not saved | Reopen the starter, rebuild only the current milestone, and add a save check halfway through each sprint |
| Blocks or panels look different | Use purpose/shape language and the current interface; do not make students hunt for an old screenshot |
| Student cannot control the pointer reliably | Provide a mouse, adjust pointer settings, use a partner navigator, or let the student direct the build aloud |
| Device or network fails | Continue with pitch, broadcast map, sprite roles, variable list, paper debugging, or playtest notes |
| Student is overwhelmed by the full architecture | Start with player + goal + one variable + restart; add only one system after that loop works |

## Placement record

Privately record `ready`, `ready with named supports`, or `bridge first`, plus the support that worked. Do not publish placement labels or rank students by speed. Recheck after the bridge; placement is a starting-point decision, not an identity.
